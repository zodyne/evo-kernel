§1

系统是什么

一句话定位

通用记忆框架（Mem0 / Zep·Graphiti / Letta / Cognee）解决的是经验的存储与检索；Evo-Kernel 解决的是其上没人解决的治理、固化、可审计。二者叠加而非替代——下层存取可换成熟框架作外挂后端，上层负责捕获规范、反馈计数、离线蒸馏、技能与约束固化、git 审查。 设计

占据的三个真空位

能力内容市面为什么没有

⑤ git-as-database目录即状态机，git mv 即流转，自带历史与 diffbasic-memory 的文件哲学最接近但无 git diff 审查；最硬的差异化点

附带两个普遍缺失的语义：helpful/harmful 双向反馈计数与失败经验一等公民（借鉴 ReasoningBank）。

对三个直接参照系的差异化

ACE arXiv 2510.04618

学术同源背书。增量 delta + helpful/harmful counters + deterministic merge，本系统已采纳。差别：ACE 优化单一 playbook、有 benchmark 评分器、进程内部署；本系统管异构多层记忆、开放真实工作、无固定评分器、harness 原生 + git + 人审。同源不同层。

SkillOpt 最直接竞品

“gradient descent for SKILL.md” + nightly 离线自演化。差别：SkillOpt 每域单一技能文档且必须有评分器。其 validation gate 被借鉴为条件触发机制（curate --validation-gate），不在路线图排期。

Claude 原生 Auto Memory + Auto Dream

存在性风险。单 harness 内覆盖「捕获 + 后台离线整合」。但闭源、单 harness、无 git、无开放标准固化、无 hook 梯度、无人审。边际价值完全由下面五点增量定义。

五点增量（自研的正当性）

  1. 开放协议层——SKILL.md 开放标准 + frontmatter 约定 + evo CLI，不焊死任一 harness。
  2. git 可审计可回滚——目录即状态机，每一笔固化/退役可 diff、可 revert。
  3. 人审固化纪律——固化/退役需人审批；计数离线对账单点回填，禁止实时回路。
  4. 跨 harness——Pi（ExtensionAPI）+ Claude Code（hooks），内核不感知 harness。
  5. 固化到开放标准 + hook 硬化梯度——warn 观察期 → block，唯一 fail-close 层有最严准入。

诚实边界：若只用 Claude Code 单 harness、且不在乎 git / 人审 / 跨平台，原生机制已覆盖相当一部分日常需求。上面五点若不能清晰交付，自研的边际价值会被持续蚕食——这是设计文档自己列出的头号存在性风险。

七条不变量（红线，每条有 smoke 守护）

I1 · fail-open 主链路

recall / 登记 / 索引 / 外挂任何故障不得阻塞 harness。除 doctor 外所有命令所有路径 exit 0。唯一例外是 guard 成功匹配的 block。

I2 · 注入资格守恒

注入通道只读人审后分区，且排除 superseded_by；inbox 与 lessons 永不注入。否则 capture 就成了绕过人审直达 context 的后门。

I3 · 人审前置

curate 是唯一入库口，负三项检查：schema 校验、敏感信息、指令样内容审查（防持久化提示注入）。

I4 · 计数单点写

helpful/harmful 只由离线对账回填（reconcile.jsonl）；实时回路已被评审证伪，禁止。

I5 · 派生物可重建

一切索引是 gitignore 的派生物，index rebuild 幂等；单一事实源永远是条目文件。

I6 · 命令面只增不减

公开命令只能新增或内部换后端，不下线、不改语义。20 → 21（doctor）→ 26，零回退。

I7 · git 写序列化

产生 commit 的命令遇 index.lock 重试而非失败；约定同一时刻单写者；重试耗尽则报错退出且不留半成品。

检索评分（当前后端 scan）

relevance = max( trigger_cover × 1.0 ,  tag_cover × 0.8 ,  body_cover × 0.5 )
            // cover = |phrase ∩ task| / |phrase|；中文走 bigram，英文过滤停用词
if (relevance < 0.2) skip

score     = relevance × VERIFIED_W × evW × typeW
            VERIFIED_W = test 1.0 | command 0.8 | human 0.6 | none 0.4
            evW        = max(0.3, ln(1 + helpful − harmful))
            typeW      = principle 1.2 | 其他 1.0

预算打包：maxChars = budget × 2（默认 budget 1500）；首条必进，其后超预算即止

四态对账：指标口径的操作性定义

这是整个系统最容易被糊弄过去的地方——设计文档为此专门写了一节，把「注入精度」从一个形容词变成可计算的量。distill 时对每个注入实例逐条判定：

态含义helpfulharmful计入
●adopted被实际采用（方案引用 / 行为遵循）+10相关 ✓
◐relevant-unused与任务相关但未被用到 —— 应用层失败00相关 ✓
○irrelevant与任务无关（注入即噪声）00不相关 ✗
▲misleading误导了执行方向0+1不相关 ✗
召回精度
(adopted + relevant-unused) ÷ 已对账实例 —— 检索层指标，M1 闸门读这个
采纳率
adopted ÷ (adopted + relevant-unused) —— 应用层指标，观察项
对账覆盖率
已对账实例 ÷ 总注入实例 —— <30% 时精度不可解读
判定者分歧率
每周期人工复核 ≥10 例，>20% 时精度同样不可解读

为什么必须拆成两层：把 relevant-unused 计入同一个成功率分子，指标就对「条目召回对了却没被用上」这类失败完全不敏感——采纳率长期为 0 的系统，只要召回还准，精度看起来依然健康。实测分叉验证了这个担心：召回精度 54%，采纳率仅 29%，两者要修的地方完全不同。
