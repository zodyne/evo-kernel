⏺ 连通性测试完成，结论很明确：km3 无法通过 pal 现有架构直接接入。

  测试结果（实测，非推测）

  用你的 MOONSHOT_API_KEY（~/.claude.json 里 multi-model MCP
  已在用的那把），直接打 Kimi 编码套餐端点 https://api.kimi.com/coding：

  ┌─────────────────────────────┬──────────────────┬────────────────────────┐
  │            协议             │       路径       │          结果          │
  ├─────────────────────────────┼──────────────────┼────────────────────────┤
  │ OpenAI 兼容（pal Custom     │ /chat/completion │ ❌ HTTP 404 resource_n │
  │ provider 实际会发的格式）   │ s                │ ot_found_error         │
  ├─────────────────────────────┼──────────────────┼────────────────────────┤
  │ Anthropic 协议（/v1/message │ /v1/messages     │ ✅ HTTP 200，正常返回  │
  │ s，x-api-key 鉴权）         │                  │                        │
  └─────────────────────────────┴──────────────────┴────────────────────────┘

  根因

  1. Kimi 的编码套餐 key 只在 Anthropic 协议端点上有效，这一点你的
  ~/graph-lab/tools/multi_model_mcp.py 里 2026-07-29
  的实测注释已经写明了，本次是二次验证，结论一致。
  2. pal 的 providers/custom.py（Custom provider）继承自 
  OpenAICompatibleProvider，只会发 OpenAI
  格式请求（/chat/completions），协议对不上，所以打到 Kimi 端点必然 404。
  3. pal/providers/ 目录下没有任何 Anthropic 协议的 provider 实现（只有 openai /
  openai_compatible / azure_openai / gemini / xai / openrouter / dial /
  custom），不是配置问题，是代码层面没这个能力。
  4. 即使协议能对上，pal 的 CUSTOM_API_URL/CUSTOM_API_KEY
  全局只有一份，当前已经指给了 GLM 的编码端点——加 Kimi 会覆盖掉 GLM，不能共存。

  结论

  不是配置没调对，是 pal 目前结构性不支持这种"Anthropic 协议 +
  编码套餐限定端点"的 provider。要接入 km3，唯一路径是给 pal 加一个新的
  Anthropic-protocol provider 类（仿 custom.py 但走 /v1/messages +
  x-api-key），这是代码改动，不是配置改动。

  你现有的 multi-model MCP 已经用正确协议连通了 kimi（✔ 
  Connected），如果只是要用 km3 的能力，直接用那个入口就是通的，不需要经过 pal。

  代码）；还是
  2. 到此为止，接受"kimi 走 multi-model、glm 走 pal"这个分工？
