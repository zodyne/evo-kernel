# 穷举标注规范（v1，2026-09-14）

## 为什么这样标

现有两套评测都无法支撑任何改动结论：bench 的 long 组只有 **4 个用例**（95% CI ≈ [0.19, 0.99]，
检不出 <0.5 的效应）；回放里 **93.6% 的丢失没有任何质量证据**（全库盲区 54%）。
根本原因是真值来源依赖 reconcile，而 reconcile 依赖 transcript（C1 已大量丢失）。

**小语料是优势**：语料只有 76 条 ⇒ 可以**穷举标注**每个 query × 每个条目（无需 pooling），
这是 IR 里小集合的标准做法，也是唯一**不依赖 transcript** 的真值路径。

## 标签定义

| 标签 | 定义 |
|---|---|
| **R** | 该条目与**当前任务本身**实质相关 —— 读到它不会觉得跑题 |
| **I** | 不相关 |

**判的是「是否相关」，不是「是否会被采用」。** 内核自己把这两个拆成两个指标：
`召回精度 = (adopted + relevant-unused)/n`、`采纳率 = adopted/(adopted+relevant-unused)`。
所以「相关但没被用上」在本标注里算 **R**。混起来会重演「形态混淆」那类错误。

## 明确不算 R 的三种情形

1. **同项目、不同子问题**（如：都是 SUC221，一个讲 CFAR 过滤、一个讲编译错误）
2. **主题词重合但主张不适用**（词面上都有"结果/文件/数据"，但结论用不上）
3. **纯背景信息** —— 不改变对当前任务的做法或判断

## 决策问句（统一用它，避免二审不一致）

> 如果 agent 在做这个任务时读到这一条，它会不会**觉得跑题**？
> 会 → **I**。不会，且确实谈的是这件事 → **R**。

## 输出格式

每个 query 一行 JSON：

```json
{"n": 1, "relevant": ["id-a", "id-b"], "borderline": ["id-c"], "why": {"id-a": "一句话依据"}}
```

- `relevant`：判为 R 的 id
- `borderline`：你拿不准的 id（**必须单独列出**，供人工复核）
- `why`：只给 borderline 和判得可能反直觉的条目写依据（不必给全部）

## 两条纪律

1. **盲**：不要去看系统实际注入了什么，也不要去读 `ops/log/recall.jsonl`。看到系统的选择再标，
   标出来的就不是真值，是对系统行为的合理化。
2. **全部 76 条都要过一遍**，不能只看"看起来相关"的那几条 —— 漏标会让召回率虚高。

## 层与区间的处理（v2 增补，2026-09-14）

### query 层

| layer | 含义 | 进指标吗 |
|---|---|---|
| `task`（缺省）| 正常的用户/agent 任务 prompt | ✅ 计入 precision/recall |
| `nontask` | 非任务 prompt（斜杠命令、系统通知、中断提示）| ❌ 只测「该不该零注入」 |
| `indeterminate` | **query 文本本身残缺** ⇒ 标注建立在残缺信息上 | ❌ 方法学上无效，排除 |

**排除必须基于先验理由。** `indeterminate` 的唯一合法依据是「query 文本不足以判定相关性」
（如被日志截断、原始 transcript 已不可寻）。**绝不能因为「它恰好是个漏」而事后排除** ——
那样会美化 recall。加层时要在 `indeterminate_reason` 里写明理由。

### 条目层：borderline **报区间**，不丢弃

标者拿不准的条目记进 `borderline`。计算时**两个边界都算**：

- **下界**：把 borderline 当 **I**（无关）
- **上界**：把 borderline 当 **R**（相关）

两个数一起报，不确定性就显式了。比「丢掉不管」诚实，也比「我替你定了」安全。

**⚠️ 两个指标的区间方向相反，别直接写「下界/上界」**：

| 指标 | 把 borderline 当相关 | 原因 |
|---|---|---|
| precision | **升** | 分母（误注入）缩小 |
| recall | **降** | 分母（应召回）长大得比分子快 |

⇒ **recall 的最坏情形是区间低端。** 曾经按「下界–上界」直写，把 recall 打成了 `[33–16%]`。

### 边界条目（不可判定的 query）长什么样

首轮 9 个 query 里出现两类：

1. **被截断**：n=1 在 `recall.jsonl` 里只有 100 字（日志上限是 500，故截断发生在记录之前），
   原始 transcript 已不可寻 ⇒ `indeterminate`
2. **信息量不足**：n=5「已经修改请扫描审查」—— 9 字、无改动对象。标者反复写「改动对象未知，
   故 borderline」（5 条）。它不是残缺，是**天生的泛指** ⇒ 留在 `task` 层，但其 borderline
   会把区间拉宽，这个宽度本身就是信息

第 2 类**不该**排除：真实检索里就是会遇到泛指 query，系统理应能处理（或明确不该处理）。
用它去测系统是对的，只是结论要带区间。
