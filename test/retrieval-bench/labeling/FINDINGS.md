# 穷举盲标结果（2026-09-14 首轮）

## 结果

| 项 | 值 |
|---|---|
| 查询 | 9 个（长/中/短 用户任务 6 + agent prompt 2 + 非任务 1）|
| 穷举规模 | 9 × 76 = **684 对**全部通读 |
| **precision** | **9/17 = 53%**，区间 [53%, 59%] |
| **recall** | **9/27 = 33%**，区间 **[16%, 33%]**（最坏情形 16%）|
| 明细 | 命中 9 · 误注入 8 · **漏 18**（漏/误 = 2.25）|
| borderline | 44 条（6%）⇒ **按下界（当 I）计**；上界见区间 |
| 排除 | n=1（`indeterminate`：query 被截断）、n=9（`nontask`）|

标注者：3 名**盲标**者（干净上下文，未读 `ops/log/recall.jsonl`、不知系统注入了什么）。
盲是硬纪律 —— 看到系统的选择再标，标出的不是真值，是对系统行为的合理化。

## ⚠️ 两个方法学错误（首版数字因此无效，必须记住）

### 错误 1：拿历史注入去比今天的条目集

首版用 `recall.jsonl` 里记录的注入集，对着**今天**的 76 条与标注算，得 22%/22%。
但那些记录跨了 7 月底到 8 月中，其间条目被退役、改名、固化进 skill ——
**9 个 query 里 5 个的注入集含有今天已不存在的条目**（n=1 的 6 条里 5 条已消失）。

⇒ 代码里对 2026-07 的查询，第 3 项里的 `independent-design-review` 等**今天根本不在现役集**。

**规则：凡"系统行为"两侧必须取自同一时刻** —— 条目集取当下，注入也必须当下跑出来。
改今天重跑后：**53% / 33%**。差距这么大，说明这个坑足以让人得出相反结论。

### 错误 2：工具路径算错，导致「所有 query 都零注入」

`run-eval.js` 写在 `test/retrieval-bench/labeling/`，而根目录取的是 `path.resolve(__dirname,'../..')`
= `<repo>/test` ⇒ 临时 ROOT 是空的 ⇒ 每个 query 都 0 注入、两数全 0。
**看起来像"系统什么都没做"，其实是环境没搭起来。**
修成 `'../../..'` 后正常。教训：**新工具第一次跑出"全 0/全空"时，先怀疑环境，别先怀疑被测对象。**

## 三条结论（数字已按今天重跑修正）

### 1. 「空命中」多数是真漏，不是正确零注入

4 个零注入的 query 里 **3 个漏了真相关**，只有 1 个（非任务 prompt）是正确零注入：

| query | 真相关 | 系统 | 判定 |
|---|---|---|---|
| n=4（58 字）| 1 | 0 | ❌ 漏 |
| n=5（9 字：「已经修改请扫描审查」）| 2 | 0 | ❌ 漏 |
| n=6（19 字：「解决当前 nvim 中出现的 lsp 报错问题」）| 1 | 0 | ❌ 漏 |
| n=9（非任务）| 0 | 0 | ✅ 正确 |

⇒ 内核记的 202 个「空命中」里，**至少有相当一部分是「够不着」而非「本就不该注入」**
（对应 `recall-failure-empty-vs-noise-taxonomy` 那条自己的分类）。这条**第一次被独立量化**。

### 2. 与内核自报的 40% 不一致，且方向重要

| 来源 | precision | 性质 |
|---|---|---|
| 内核自报 | 40%（90/225）| reflector 判定，**54% 盲区**，依赖 transcript |
| 本集 | **22%** | 独立盲标，穷举 76 条，**不依赖 transcript** |

两者口径不同、不能直接相等。但**本集测出了内核自报测不出的东西**：
**漏（18）是误（8）的 2.25 倍** —— 而内核的指标此前只盯 precision（且一半盲区）。
这是本集最重要的产出：**它给出了"该往哪边优化"的直接读数**，而内核原有指标给不出。

### 3. 规范本身要改：44 条 borderline（6%）

标者反复写「**改动对象未知，故 borderline**」（n=5 尤其明显：9 字 query）。
这不是标者的问题，是**query 信息量不足** —— 说明：

- 我们的 query 集里混有**信息不足以判定相关性**的短 prompt
- 「决策问句」对这类 query 判别力不足，应补一条兜底：**信息不足 → 该 query 不进 precision/recall 的分子分母，
  单列「不可判定」层**

## 已知局限（不要过度读这份结果）

1. **n 小**：7 个有效 query、27 个真相关对 ⇒ 区间宽，方向可信、点数不精确。
2. **44 条 borderline 按下界计** ⇒ 若它们多数实为 R，**recall 降到 16%**（结论方向不变、更差）。
3. **n=1 的 query 在 recall.jsonl 里被截到 100 字**（停在「调研范围：1.」），按可见部分判定，建议补全后复标。
4. 标注者是 LLM，非用户本人 —— 已是**独立且盲**的判定，但终究不是领域专家的真值。

## 下一步（按证据排序）

1. **补全并复标 n=1**，再把 query 集从 9 扩到 ~20（含更多短 query，以验证第 3 条）。
2. **修规范**：加「不可判定」层（第 3 条）。
3. **优化方向从 precision 转到 recall**：文献侧（retriever–reader：检索召回是端到端上限）
   与本集（漏 28 = 误 28）**同向**，且本地实测**预算只有 3% 打满**（中位注入 770/3000 字符）
   ⇒ 多注入的边际成本低，漏的边际成本高。
4. 在此之后才谈评分改动 —— 且改动必须**同时**报 precision 与 recall，不能只报一个。

# 第二轮（同日）：query 集 9 → 20

## 结果

| 项 | 9 条（第一轮）| **20 条（第二轮）** |
|---|---|---|
| 有效 query | 7 | **17**（跳 `indeterminate` 2 + `nontask` 1）|
| precision | 53% [53,59] | **57% [57,62]** |
| recall | 33% [16,33] | **28% [10,28]**（最坏 10%）|
| 命中 / 误 / 漏 | 9 / 8 / 18 | **12 / 9 / 31** |
| **漏/误** | 2.25 | **3.44** |

**扩大样本后结论从"倾向"变成"决定性"：漏/误从 2.25 升到 3.44，约束在召回侧。**
且 recall 最坏情形从 16% 降到 **10%** —— 加重短 query 后更差，说明短 query 是重灾区而非样本噪声。

## 短 query 的失效形态

17 个有效 query 里 **8 个零注入，其中 7 个漏了真相关**：

| query | 真相关 | 实注入 |
|---|---|---|
| n=4（公司内网中转站）| 1 | 0 |
| n=5（已经修改请扫描审查）| 2 | 0 |
| n=6（nvim LSP 报错）| 1 | 0 |
| n=14（为 43.201 装 hermes）| 1 | 0 |
| n=15（你来修改并记录）| 1 | 0 |
| n=17（多模型分析解决方案）| 2 | 0 |
| n=18（nvim 通用工程目录结构）| 1 | 0 |
| n=20（大重构 分阶段 闸门 逐位不变）| 1 | 0 |
| **n=16（macOS 上 timeout 命令用不了）** | 1 | **1 ✅** |
| n=19（deepseek 为什么慢）| 0 | 0 ✅ 正确 |

**唯一命中的短 query 是 n=16** —— 它的 query 与条目 `macos-no-timeout-command` **字面高度重合**。
⇒ **短 query 只在词面撞上时才命中**，这正是 §11 问题 1（词汇失配）的量化形态，
而不是"短 query 信息太少所以检索本来就难"。

## 「信息量不足」被独立复现

第二轮 3 名盲标者（与第一轮不同的人）**自发**用同样口径标出同一现象：

| query | borderline 数 | 对象明确度 |
|---|---|---|
| n=16（macOS timeout 用不了）| **0** | 完备 |
| n=13（按报告简化 latex）| 1 | 指定文件 |
| n=18（nvim 多种工程目录）| 2 | 明确 |
| n=11（审查指定分支）| 9 | 明确但任务复杂 |
| n=14（装 hermes）| 3 | 明确 |
| **n=15（你来修改并记录）** | **6** | **无宾语** |
| **n=17（多模型分析解决方案）** | **5** | **对象不明** |
| **n=19（deepseek 为什么慢）** | **6** | **调用链不明** |
| **n=20（关键词串）** | **6** | **对象不明** |
| **n=10（100 字截断）** | **12** | **截断** |

**n=10 由标者主动建议归 `indeterminate`**，理由措辞是「query 文本不足以判定相关性，
而非『它恰好是个漏』」—— 与本库自定的排除原则（必须基于先验理由）一致。

⇒ 结论：**borderline 的宽度是 query 信息量的函数**，不是标者不一致。
信息量不足的 query 会把区间拉宽，**这个宽度本身就是测量结果**，不该被抹平。

# 第三轮：可靠性曲线与阈值扫描（1292 对全标注）

**做这件事的理由**：第三轮文献查证指出，代价闭式解 `P(R|d) > C_FP/(C_FP+C_FN)` **只在分数是校准概率时成立**，
并明确说改完阈值机制后"下一个该看**分数对真相关的单调性/可校准性**（reliability 曲线）"。

## 可靠性曲线

| 分数区间 | 配对数 | 真相关数 | **P(相关)** |
|---|---|---|---|
| 0.00–0.05 | 982 | 8 | **1%** |
| 0.05–0.10 | 173 | 6 | **3%** |
| 0.10–0.15 | 77 | 6 | **8%** |
| 0.15–0.20 | 27 | 2 | **7%** |
| 0.20–0.25 | 14 | 4 | **29%** |
| 0.25–0.30 | 8 | 6 | **75%** |
| 0.30–0.35 | 5 | 2 | 40% |
| 0.35–0.45 | 4 | 4 | 100%（n=4，不可读）|
| ≥0.45 | 2 | 0 | 0%（n=2，不可读）|

基率 P(相关) = 38/1292 = **2.9%**。

**结论**：分数**确实单调携带信号**（1%→3%→8%→29%→75%），到 0.30 为止；
但**不是校准概率** —— 0.25 处的真实相关率是 **75%**，分数在阈值附近**严重低估**相关率。
⇒ 该分数**可排序、不可直接当概率**用；任何依赖"校准概率"的公式都不能直接套。

## 阈值扫描

| 阈值 | 注入数 | 命中 | precision | recall |
|---|---|---|---|---|
| 0.100 | 137 | 24 | 18% | **63%** |
| 0.150 | 60 | 18 | 30% | 47% |
| 0.200 | 33 | 16 | 48% | 42% |
| **0.225**（代价闭式解）| 25 | 15 | **60%** | **39%** |
| **0.250**（当前）| 19 | 12 | **63%** | 32% |
| 0.300 | 11 | 6 | 55% | 16% |
| 0.400+ | 4 | 2 | 50% | 5% |

**两条读数**

1. **文献由漏/误=3.44 算出的闭式最优阈值 0.225，与实测曲线吻合**（60%/39% 对 63%/32%）。
   移到最优点只买 **+7pp recall / −3pp precision** ⇒ **阈值已在最优点附近，挪它不是杠杆。**
2. 🔴 **降到 0.10 也只有 63% recall**（而 precision 崩塌到 18%）
   ⇒ **37% 的真相关对在词法上完全够不着，任何阈值都救不了。**

## 这否掉了「只准改一处 = 改阈值机制」的答案

文献的建议（拆开"排序"与"是否注入"两职、用 per-query 分布定 cut）在**机制上正确**，
但**在本系统上不是杠杆**：阈值已在最优点附近，全部空间只有 7pp。

**真正的杠杆是那 37% 的词汇失配** —— 而那是词法层结构上做不到的事。

**内核自己早就写过这件事**：`rerank-channel-design` 的**形态 B「主 agent 即大模型精筛器」**
（`evo candidates` 粗筛清单 + `evo get --ids` 拉全文，零额外模型调用）。
⇒ **语义匹配交给 agent**，词法层的职责应从「高精度注入」改成「**高召回短名单**」。

**反向推论**：本会话新加的两道闸门（`noisyPrompt` 噪声门、低精度条目排除）
都在**减少注入**，即**压低召回** —— 当时只测了精度一侧。同一条错误的第三次复发。
