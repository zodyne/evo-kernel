| 项 | 值 |
|---|---|
| 查询 | 9 个（长/中/短 用户任务 6 + agent prompt 2 + 非任务 1）|

| **recall** | **9/27 = 33%**，区间 **[16%, 33%]**（最坏情形 16%）|

盲是硬纪律 —— 看到系统的选择再标，标出的不是真值，是对系统行为的合理化。

## ⚠️ 两个方法学错误（首版数字因此无效，必须记住）

### 错误 1：拿历史注入去比今天的条目集

首版用 `recall.jsonl` 里记录的注入集，对着**今天**的 76 条与标注算，得 22%/22%。
但那些记录跨了 7 月底到 8 月中，其间条目被退役、改名、固化进 skill ——
**9 个 query 里 5 个的注入集含有今天已不存在的条目**（n=1 的 6 条里 5 条已消失）。

⇒ 代码里对 2026-07 的查询，第 3 项里的 `independent-design-review` 等**今天根本不在现役集**。

**规则：凡"系统行为"两侧必须取自同一时刻** —— 条目集取当下，注入也必须当下跑出来。
改今天重跑后：**53% / 33%**。差距这么大，说明这个坑足以让人得出相反结论。

### 错误 2：工具路径算错，导致「所有 query 都零注入」

`run-eval.js` 写在 `test/retrieval-bench/labeling/`，而根目录取的是 `path.resolve(__dirname,'../..')`
= `<repo>/test` ⇒ 临时 ROOT 是空的 ⇒ 每个 query 都 0 注入、两数全 0。
**看起来像"系统什么都没做"，其实是环境没搭起来。**
修成 `'../../..'` 后正常。教训：**新工具第一次跑出"全 0/全空"时，先怀疑环境，别先怀疑被测对象。**

## 三条结论（数字已按今天重跑修正）

### 1. 「空命中」多数是真漏，不是正确零注入

4 个零注入的 query 里 **3 个漏了真相关**，只有 1 个（非任务 prompt）是正确零注入：

| query | 真相关 | 系统 | 判定 |
|---|---|---|---|
| n=4（58 字）| 1 | 0 | ❌ 漏 |
| n=5（9 字：「已经修改请扫描审查」）| 2 | 0 | ❌ 漏 |
| n=6（19 字：「解决当前 nvim 中出现的 lsp 报错问题」）| 1 | 0 | ❌ 漏 |
| n=9（非任务）| 0 | 0 | ✅ 正确 |

⇒ 内核记的 202 个「空命中」里，**至少有相当一部分是「够不着」而非「本就不该注入」**
（对应 `recall-failure-empty-vs-noise-taxonomy` 那条自己的分类）。这条**第一次被独立量化**。

### 2. 与内核自报的 40% 不一致，且方向重要

| 来源 | precision | 性质 |
|---|---|---|
| 内核自报 | 40%（90/225）| reflector 判定，**54% 盲区**，依赖 transcript |
| 本集 | **22%** | 独立盲标，穷举 76 条，**不依赖 transcript** |

两者口径不同、不能直接相等。但**本集测出了内核自报测不出的东西**：
**漏（18）是误（8）的 2.25 倍** —— 而内核的指标此前只盯 precision（且一半盲区）。
这是本集最重要的产出：**它给出了"该往哪边优化"的直接读数**，而内核原有指标给不出。

### 3. 规范本身要改：44 条 borderline（6%）

标者反复写「**改动对象未知，故 borderline**」（n=5 尤其明显：9 字 query）。
这不是标者的问题，是**query 信息量不足** —— 说明：

- 我们的 query 集里混有**信息不足以判定相关性**的短 prompt
- 「决策问句」对这类 query 判别力不足，应补一条兜底：**信息不足 → 该 query 不进 precision/recall 的分子分母，
  单列「不可判定」层**

## 已知局限（不要过度读这份结果）

1. **n 小**：7 个有效 query、27 个真相关对 ⇒ 区间宽，方向可信、点数不精确。
2. **44 条 borderline 按下界计** ⇒ 若它们多数实为 R，**recall 降到 16%**（结论方向不变、更差）。
3. **n=1 的 query 在 recall.jsonl 里被截到 100 字**（停在「调研范围：1.」），按可见部分判定，建议补全后复标。
4. 标注者是 LLM，非用户本人 —— 已是**独立且盲**的判定，但终究不是领域专家的真值。

## 下一步（按证据排序）

1. **补全并复标 n=1**，再把 query 集从 9 扩到 ~20（含更多短 query，以验证第 3 条）。
2. **修规范**：加「不可判定」层（第 3 条）。
3. **优化方向从 precision 转到 recall**：文献侧（retriever–reader：检索召回是端到端上限）
   与本集（漏 28 = 误 28）**同向**，且本地实测**预算只有 3% 打满**（中位注入 770/3000 字符）
   ⇒ 多注入的边际成本低，漏的边际成本高。
4. 在此之后才谈评分改动 —— 且改动必须**同时**报 precision 与 recall，不能只报一个。
