# 委派批量整理活，提示词必须给「每项调用预算 + 必须落笔」，否则它会一直读而不写

## 主张

把「N 项，每项＝读两份文件 + 判断 + 改写」这类批量整理活委派给后台 agent 时，提示词里只写**目标**不够，必须同时给两条约束：

1. **每项的动作预算**（例：每对最多 2 次工具调用），并明说禁止重读已读过的文件；
2. **必须落笔**（每项都要产生一次 `edit` 或删除），并给硬时限与"做不完就砍范围并报告"的许可。

缺这两条的委派，agent 会无限期地读下去：实证是同一份 16 项的合并任务，**31 分钟 / 24 次工具调用 / 45.8k token 之后，磁盘上零改动**（16 个提案原封不动、目标条目一个没改）。加上这两条并重新下达后，剩余工作十几分钟就落完。

## 为什么

"读"永远比"写"安全，所以缺乏约束的 agent 会停在前者 —— 尤其在任务含"判断"成分（该不该补？补什么？）时，读取看起来总像在推进。而**进度只能用落笔衡量**：工具调用数、token 数、自述进度都不构成产出证据。

由此还有一条实操推论：**判断委派死活要看文件系统，不看它的自述**。同一次事故里，agent 的上下文占用正常、调用数在涨，从"它还在工作"的任何间接指标看都健康；只有 `git status` / `ls` 这种外部事实能揭穿"零产出"。

## 反例 / 边界

- 不是所有委派都要预算：**探索型**任务（"找出这批文件里所有重复的条目"）就该允许自由读，产出是报告而非落笔。本条针对的是**已知项数的整理型**任务。
- 预算给得太紧会伤质量：每项 2 次调用意味着不能反复交叉核对。适用于"判断依据在文件里、不需要额外取证"的活；需要验证的要另配（如本库用独立核验代理专门做验证）。
- 提示词里若有"拿不准就更保守"之类的取舍指示，会**系统性偏移结果分布**，报告时要一并说明。实证：同一次合并里，"拿不准就补而不是删"这句话让 16 项里 15 项判为"需补写"——该比例不能读作内容判断的结果。
- 与 `stop-condition-on-hour-scale-metric-is-not-a-stop-condition` 是邻居但不同：那条讲**等待型** agent 的判据时标，本条讲**整理型** agent 的落笔约束。前者表现为"一直挂着"，后者表现为"一直在读"。

## 证据

- 事故：16 项合并任务，委派后 31 分钟零写盘。判据取自文件系统（`ls ops/proposals/` 仍 16 个文件、`git status` 无被改条目），而非其自述。
- 修正：重新下达「每对 ≤2 次调用 / 必须落笔 / 不许重读 / 15 分钟硬时限 / 做不完就砍范围并报告」，随后 16 项全部落完（15 补写 1 纯删，14 个目标文件，39 增 28 删）。
- 同型任务第二次（5 项）直接沿用收紧后的提示词，一次通过、无卡顿。
