# 开放式任务配文件工具没有终止条件：先把材料做全，再决定给不给工具

## 主张
委派任务时，决定工具权限的**首要变量是任务有没有完成判据**，不是材料看着全不全。
"回答这两个问题"答完就停；"找出所有问题"永远可以再核实一处——后者一旦有文件读取工具，
模型会不断扩大搜索面直到耗尽预算或需人工中断。

处方有**顺序**：**先把材料补全（见 `review-packet-completeness-is-assemblers-duty`），
再决定给不给工具**。顺序颠倒会踩坑：材料不全时抽掉工具，等于堵死评审员唯一的自救路径，
它只能照残缺材料下结论。

## 为什么
同一模型、同一工具集，任务形态不同，工具用量差两个数量级：

| 任务 | 工具 | read 调用 | 结果 |
|---|---|---|---|
| 读一个文件回答两个具体问题（封闭） | `-t read` | **16 次** | 正常返回，答案正确 |
| 评审 382 行 diff 评审包（开放） | `-t read` | **2306 次** | 62 MB 事件流、2 次自动重试、手工 kill |
| 同一个评审包（开放） | `-nt` | **0 次** | 正常返回，8 条发现、4 条属实 |

## 证据的已知缺陷（本条自身的边界，不可略过）
上表第 2 行那个跑飞的评审包，**同时还材料不全**（需求段只贴了 4 轮、diff 覆盖 6 轮产物）。
因此"开放性"与"材料不全"两个因素**在本次证据里没有解耦**——跑飞可能由任一或两者共同造成。
缺的对照是"材料确实完整的开放式任务 + 工具"，本次没有该数据点。

与第 1 行的对照同样不干净：那次任务在**封闭性**和**自包含性**上都与第 2 行不同。
故本条的证据强度只到"开放式 + 材料不全 + 工具 → 跑飞"，主张里"开放性是首要变量"
是推理外推，未被单独验证。**未来若出现材料完整仍跑飞（或材料补全后不再跑飞）的实例，
应回来修订本条的归因。**

## 边界 / 反例
- **不是"永远别给子 agent 工具"**。探索未知范围的任务（"这仓库哪里实现了 X"）必须给，
  它的终止判据是"找到了"，天然存在。
- **代码评审里真正的自包含极少**：diff 几乎总引用未贴进来的上下文（被改函数的调用方、
  未改动的头文件、依赖契约）。此时抽掉工具会换来一份**浅评审**——漏掉只在上下文里可见的
  问题，或把不确定的猜成问题，而使用者还以为已按经验行事。这类场景应当**给工具但限定范围**
  （指定可读路径 / 设调用次数上限），而不是二选一。
- 判据是终止条件而非任务大小：小而开放（"看看这函数有没有隐患"却不给源码）同样会跑飞。

## 失败信号（未来命中即该想起本条）
- 子 agent 迟迟不返回，输出文件体积以百 MB 计。
- 工具调用计数远超任务涉及的文件数。
- 你在等一个"应该几十秒就好"的评审。
